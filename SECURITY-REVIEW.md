# Security review

**Status:** source review, audit cross-check, test-first/fix evidence, and migration validation are recorded below. C-05, C-07 beyond structural dimensions, and C-08 remain open review candidates; C-04 is a documented asset compatibility limit.

**Baseline:** tag `v0.3.0`; findings are identified as preexisting or migration-introduced against the completed SDK migration and security-fix commits.

**Evidence status:** source and audit-report review, red/fix commits for confirmed defects, SDK TestVM unit tests, SDK devnet E2E, fuzz/property runs, differential vectors, coverage comparison, benchmarks, strict Clippy, formatting, and Wasm checks are recorded after the finding table. Fee-on-transfer probes confirmed that nominal share accounting requires exact-transfer assets; committed tests and docs state that limit explicitly.

## Scope

The requested review scope is the whole library: `contracts/src/**`, `contracts-proc/src/**`, `lib/crypto/src/**`, examples, benches, fuzz targets, docs, and the SDK devnet test setup replacing the legacy E2E framework. I reviewed audited production source, the SDK-related production diff, changed storage declarations, and the TestVM fixture, then ran the migrated unit and devnet suites, fuzz/property targets, example activation, benchmarks, and coverage comparison. Storage compatibility was reviewed from source and documented for changed extension/example layouts.

The three audit PDFs under `audits/` were reviewed for their findings and stated resolution status. Audit statements that a finding was resolved are not, by themselves, proof that the fix is correct in this checkout.

## Invariants to preserve and test

These are review targets inferred from the library’s APIs, implementation, and standards. Listing an invariant does not assert that it has been proven or that all edge cases have been tested.

### Access control and finance

- **`Ownable` and `Ownable2Step`** (`contracts/src/access/ownable.rs`, `ownable_two_step.rs`): only the current owner may perform owner-gated operations; ownership transfer cannot be accepted by an unrelated account; renunciation and zero-address behavior match the documented policy.
- **`AccessControl`** (`contracts/src/access/control/mod.rs`): role membership is authoritative; only each role’s admin can grant/revoke it; renounce applies only to the caller; role-admin changes and emitted events agree with stored state.
- **`AccessControlEnumerable`** (`contracts/src/access/control/extensions/enumerable.rs`): each role’s member set contains exactly its members, with no duplicates; grant/revoke/renounce keep the set and base role state synchronized.
- **`VestingWallet`** (`contracts/src/finance/vesting_wallet.rs`): vested amount is zero before start, monotone during vesting, and reaches total historical allocation at/after end; released amounts never exceed vested amounts or total allocation; release transfers only the newly releasable amount; native and ERC20 accounting remain independent. Accounting assumes exact-transfer, non-rebasing ERC20s. A negative rebase can make current balance lower than tracked releases and temporarily underflow releasable calculations; on chains where the native currency also has an ERC20 representation, native and ERC20 withdrawal entrypoints can address the same asset independently. Full-precision intermediate arithmetic is covered by fixed finding C-03.

### Token contracts and extensions

- **`Erc20`** (`contracts/src/token/erc20/mod.rs`): balances sum to total supply; transfer/mint/burn preserve that relationship; allowances cannot underflow; approvals and transfers reject invalid zero-address cases as specified; `transfer_from` spends allowance and transfers atomically.
- **ERC20 burnable/capped** (`erc20/extensions/burnable.rs`, `capped.rs`): burns reduce balances and supply exactly once; all mint paths enforce `total_supply <= cap`.
- **ERC20 metadata and permit** (`erc20/extensions/metadata.rs`, `permit.rs`, `utils/nonces.rs`, `utils/cryptography/eip712.rs`): metadata does not alter token accounting; permit signatures bind the intended domain, owner, spender, value, and nonce; each valid nonce is consumed once; invalid/replayed signatures do not change allowance.
- **ERC20 flash mint** (`erc20/extensions/flash_mint.rs`): temporary minting is bounded by the advertised maximum; callback and repayment checks enforce the required return and fee; successful completion restores the supply invariant, while callback failure reverts the whole operation.
- **ERC20 wrapper** (`erc20/extensions/wrapper.rs`): under exact-transfer assets, outstanding wrapper supply tracks backing; no-code underlying calls fail. Fee-on-transfer assets are documented as unsupported (C-04).
- **ERC4626** (`erc20/extensions/erc4626.rs`): conversions and previews follow the documented rounding direction; share supply and asset custody stay coherent through deposits, mints, withdrawals, and redemptions; allowance and max-limit checks are enforced; external token callbacks cannot observe an invalid intermediate vault state. Exact-transfer assets are required by the documented support policy (C-04).
- **`SafeErc20`** (`erc20/utils/safe_erc20.rs`): successful calls accept only the intended return-data cases; failed calls or false returns fail atomically; relaxed ERC1363-style helpers preserve their documented semantics.
- **`Erc721`** (`contracts/src/token/erc721/mod.rs`): each live token has exactly one owner; owner balances match ownership; approvals cannot authorize unrelated tokens or operators; transfer/mint/burn clear or update approvals and balances correctly; safe transfers enforce receiver acceptance.
- **ERC721 extensions** (`erc721/extensions/**`): burnable operations preserve core ownership/supply; enumerable indexes match core owner balances, including token ID zero; metadata and URI storage expose the expected URI only for valid tokens; consecutive minting assigns a bounded contiguous ID range only during construction; wrapper operations preserve the underlying-token custody and ownership relationship.
- **`Erc1155`** (`contracts/src/token/erc1155/mod.rs`): balances and batch operations are consistent per `(owner, id)`; approvals authorize only the intended operator; mint/burn and supply tracking agree; safe single/batch transfers enforce receiver acceptance and revert atomically on rejection.
- **ERC1155 extensions and receiver** (`erc1155/extensions/**`, `erc1155/receiver.rs`, `erc1155/utils/holder.rs`): burnable/supply/URI extensions preserve base balances and URI semantics; receiver hooks return the required selectors; rejected transfers leave balances unchanged.
- **ERC2981** (`contracts/src/token/common/erc2981.rs`): receiver is nonzero when a royalty is set; numerator does not exceed a nonzero denominator; token-specific royalty takes precedence over the default; returned royalty is floor(`sale_price * numerator / denominator`) and cannot exceed sale price. Zero-as-uninitialized denominator and full-precision arithmetic are fixed findings C-01/C-02.

### Proxies and shared utilities

- **ERC1967 proxy utilities** (`contracts/src/proxy/erc1967/**`): implementation/admin/beacon slots use the standard slot values; upgrades validate implementation code and emit compatible events; delegate calls preserve caller/value and propagate revert data.
- **Beacon proxy and upgradeable beacon** (`contracts/src/proxy/beacon/**`): proxy implementation always comes from its beacon; only authorized owners can change the beacon implementation; implementation addresses remain valid contracts and upgrades affect all attached proxies as documented.
- **UUPS / ERC1822** (`contracts/src/proxy/utils/**`): upgrades execute only through the intended proxy context and authorization path; implementation UUID matches the ERC1967 implementation slot; incompatible implementations are rejected; initializer/version storage remains proxy-local and storage-compatible across upgrades.
- **Pausable and ERC165** (`contracts/src/utils/pausable.rs`, `introspection/erc165.rs`): pause state gates every operation documented as pause-protected; pause authority is explicit in the consuming contract; ERC165 reports only interfaces the router actually implements, including custom-selector cases (candidate C-05/C-06).
- **Nonces, EIP-712, ECDSA, P256** (`utils/nonces.rs`, `utils/cryptography/**`, `utils/precompiles/p256_verify.rs`): signature checks bind the right domain and message; nonces cannot replay; invalid scalar/point encodings are rejected; ECDSA/P256 malleability behavior matches the documented API.
- **Address, math, storage slots** (`utils/address.rs`, `utils/math/**`, `utils/storage_slot.rs`): address calls distinguish code/no-code behavior as documented; checked math reverts on true overflow and does not reject representable full-precision results; storage slots do not collide with ordinary contract storage or standard proxy slots.
- **Bitmap, enumerable set, checkpoints** (`utils/structs/**`): bitmap operations affect only the intended bit; enumerable sets contain unique elements and maintain array/index bijection; checkpoint keys are ordered and historical lookup returns the correct prior value at boundaries.

### Cryptography and proc macros

- **`lib/crypto` arithmetic and fields** (`lib/crypto/src/arithmetic/**`, `field/**`): arithmetic matches the stated limb width and modulus; checked/constant-time APIs satisfy their documented error/timing claims; conversions preserve value or fail explicitly.
- **Curve and EdDSA code** (`lib/crypto/src/curve/**`, `eddsa.rs`): point operations preserve curve/subgroup membership; decoding rejects malformed points; signature verification rejects invalid keys and signatures; secret-dependent signing operations do not leak key/nonce information through observable timing (candidate C-08).
- **Poseidon2 and Pedersen** (`lib/crypto/src/poseidon2/**`, `pedersen/**`): built-in parameter sets match reference vectors; custom parameter dimensions and cryptographic constraints are valid; sponge absorb/squeeze behavior and domain handling are unambiguous (candidate C-07).
- **Merkle proofs and Keccak** (`lib/crypto/src/merkle.rs`, `keccak.rs`): proof verification binds leaf, branch ordering, and root; custom-builder verification states any commutativity assumption; hash byte encodings are unambiguous.
- **`#[interface_id]` proc macro** (`contracts-proc/src/interface_id.rs`): generated interface IDs match the selectors routed by public implementations; duplicate or colliding selectors within a trait are rejected; selector type canonicalization agrees with Solidity ABI encoding. Cross-checking a trait's custom selector against a consumer's public router remains an integration obligation (C-05); four-byte collisions within an interface are fixed (C-06).

## Migration security review

### Source-level delta reviewed

The SDK migration production diff was compared against v0.3.0. No confirmed migration-introduced production vulnerability was found in that source review. Security-relevant changes observed:

- Global sender/value/block/contract/log access moved to `self.vm()` or an explicit VM host. The values are read from the same call context; caller authorization and event fields remain tied to the current message sender.
- External interfaces now receive an explicit VM and `Call`. Stateful ERC20/ERC721/ERC1155 callbacks continue to use mutating contexts; view calls use readonly contexts. Safe token paths retain code checks, optional-return handling, and false-return rejection.
- `AddressUtils` and ERC1967 utilities now use VM-backed code-size and storage operations. EIP-1967 implementation/admin/beacon slot constants and update ordering remain intact. `BeaconProxy` keeps its legacy ordinary `beacon` field reserved for layout compatibility but resolves the canonical EIP-1967 beacon slot to avoid implementation-storage collision.
- UUPS `only_proxy` retains the logic flag, nonzero implementation slot, and stored-version checks. Upgrade implementation/beacon paths validate code and propagate call failures.
- ERC721/1155 safe receiver checks still skip EOAs and validate the receiver selector; state changes precede callbacks and callback failure returns an error for transaction rollback. Consecutive ERC721 batch mint now uses VM code size to enforce constructor-only behavior.
- The EdDSA verifier adds explicit rejection of identity/out-of-subgroup public keys and `R` points. No regression was found against the audited zeroization, curve, conversion, P256 low-s, or EIP-712 paths.
- No production storage fields were added by the SDK migration. The ERC721 token-zero fix also preserves its original layout by deriving bounds from core balances; the preexisting `BeaconProxy::beacon` field remains present and is explicitly reserved. Unrelated arithmetic and no-code wrapper fixes are separately documented above.

### Test and storage notes

TestVM tests cover local state and call behavior. The SDK devnet E2E suite exercises deployed proxy delegatecalls, proxy storage, constructor initialization, revert propagation, upgrade authorization, and implementation isolation; those proxy and beacon scenarios pass. The TestVM mock response issue and its test-only patch are recorded as C-18.

The new `test_support::expect_error` helper restores its captured TestVM snapshot when used. A direct assertion on an `Err` value does not invoke that rollback helper, so failure tests that mutate state before returning an error must use `expect_error`/`unwrap_error` or explicitly verify rollback through a transaction-level test.
